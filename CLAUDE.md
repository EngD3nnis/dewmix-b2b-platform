## What this project is

**Dewmix Hardware** — a B2B hardware & construction materials **catalog and inquiry platform** for Kenya, expanding to East Africa. Mobile-first. WhatsApp-native. 4,000 SKUs at launch, engineered for 100k+ users.

This is **not** an e-commerce store. There is no cart, no checkout, no payment integration, and no public price display. Customers browse the catalog, see specs and stock status, and contact the business via WhatsApp with a structured, prefilled message. The business converts on WhatsApp.

**Brand voice:** confident, engineered, trustworthy. Not loud. Not playful. Solid.

**Visual identity:** blue and white. Dark mode supported. See `apps/web/src/styles/globals.css` for tokens.

## The non-negotiables

1. **No public prices.** `priceCents` exists on `Product` for internal cost tracking only and must never be serialized on public API responses or rendered in the storefront. This is a catalog + inquiry platform; pricing is negotiated on WhatsApp.
2. **No cart, checkout, or payment code.** If a feature request leads you toward any of those, push back — that's a different product. The inquiry pipeline (`Inquiry` model + WhatsApp deeplinks) is the only conversion path.
3. **IDs are UUIDv7** generated by Postgres (`uuid_generate_v7()`). Never `uuid_generate_v4()` for new tables.
4. **Server Components by default** in `apps/web`. Add `'use client'` only when you genuinely need state, effects, or browser APIs.
5. **Validate every input with Zod** before it touches business logic. DTOs live in `packages/types`.
6. **Soft delete** customer-facing entities (`deletedAt`). Hard delete only for admin tooling and audit-exempt records.
7. **Every state-changing admin action writes to `AuditLog`.** No exceptions.
8. **Phone-first auth for customers.** Email is optional. WhatsApp requires a phone number anyway.
9. **No raw SQL with user input.** Prisma parameterizes. If you ever feel the need for `$queryRawUnsafe`, stop and ask.
10. **Cache-Control headers are mandatory** on public API endpoints. Pick a TTL. Document it.
11. **Analytics must be fire-and-forget.** `ProductEvent` writes use `sendBeacon`; the endpoint swallows errors. Analytics never blocks or fails a user action.
12. **Every PR runs `pnpm lint && pnpm typecheck` before review.** CI enforces it; do it locally too.

## Folder conventions

```
apps/
  api/    NestJS backend
  web/    Next.js storefront + admin
packages/
  db/     Prisma schema + generated client (@dewmix/db)
  types/  Shared TS types + Zod schemas (@dewmix/types)
  utils/  Pure helpers — currency, dates, formatting (@dewmix/utils)
  config/ Shared ESLint, TS, Tailwind configs (@dewmix/config)
```

Inside `apps/api/src/modules/`: **group by feature**, not by type. Each module owns its controllers, services, DTOs, and tests.

Inside `apps/web/src/components/`: **co-locate by surface**. `product/` has product-specific components. `ui/` is ShadCN primitives only.

## Conventions Claude must follow

### When adding a NestJS endpoint
1. Create or extend a DTO in `packages/types/src/<feature>.ts` with a Zod schema.
2. Add the route to the appropriate module controller.
3. Apply `@UseGuards(JwtGuard, RolesGuard)` and `@RequirePermissions(...)` as needed.
4. Validate with `ZodValidationPipe` — never `class-validator`. We use Zod everywhere.
5. Return a typed response — never `any`.
6. If it mutates state, write to `AuditLog` from the service.
7. Add a Cache-Control header for public reads.
8. Write an integration test (Vitest + supertest).

### When adding a Next.js route
1. Server Component first. Drop to client only when justified.
2. Data fetching with `fetch()` + `next.revalidate` and `tags` for cache invalidation.
3. Loading and error states (`loading.tsx`, `error.tsx`) are not optional.
4. Use `<Link prefetch>` for navigation between catalog pages.
5. Images via `next/image` with explicit `width`, `height`, and `sizes`.
6. SEO: `generateMetadata()` on every public route.
7. Use semantic tokens (`bg-background`, `text-foreground`) — never hardcoded `bg-white`.

### When writing a UI component
1. Check `components/ui/` first — extend, don't duplicate.
2. Variants via `cva`. No conditional className spaghetti.
3. Theme-aware: test in both light and dark before committing.
4. Tap targets ≥ 44×44px.
5. Loading, empty, and error states are part of the component, not afterthoughts.
6. Lucide icons only. No mixed icon libraries.

### When changing the database
1. Edit `packages/db/prisma/schema.prisma`.
2. Run `pnpm db:migrate` locally with a descriptive name: `pnpm db:migrate --name add_quote_request_status`.
3. Migrations must be **backward compatible** with the previous code version.
4. Destructive changes happen as two deploys: expand → migrate code → contract.
5. Run `EXPLAIN ANALYZE` on any new query that hits a list endpoint.

## Anti-patterns to refuse

- "Let's just show the price on the catalog for now" — **no**. Pricing is negotiated on WhatsApp. The platform must never publicly display `priceCents`.
- "Let's add a cart so customers can checkout" — **no**. This is a catalog + inquiry platform. If checkout becomes a real requirement, that's a product pivot and needs a written ADR + leadership sign-off, not a PR.
- "Let's use class-validator since we have it" — **no**, Zod everywhere for consistency.
- "I'll add a 'use client' to the whole tree" — **no**, push the boundary down to the smallest interactive component.
- "Let's call the third-party API directly from the controller" — **no**, wrap it in an injectable service in `infrastructure/`.
- "We can skip the migration name" — **no**, future-you will need to read it.
- "Just trust the request body" — **no**, validate every field. Mass assignment is a real exploit.
- "Let's bypass the Inquiries service and write to the DB directly from the route" — **no**, business logic lives in services.
- "Let's `await` the analytics POST so we know it landed" — **no**. Click tracking is fire-and-forget via `sendBeacon` and the API endpoint swallows errors. A failed event is lost analytics, not a failed user action.

## How Claude should plan before coding

For any feature larger than ~50 lines:

1. State the feature in one sentence.
2. List the files to be touched.
3. Identify the module boundary it lives in.
4. Note any new dependencies.
5. Identify the cache invalidation strategy.
6. Identify the test plan.
7. **Then** write code.

For trivial changes (typo, single-line tweak), skip the plan and just do it.
